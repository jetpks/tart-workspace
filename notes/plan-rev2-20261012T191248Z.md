ENTRY P1

ITERATION: editor-multiline

OWNER-NAMED SHOW-STOPPER (live report 2026-10-12): when the cursor reaches the
end of the editing row, tart keeps accepting input but renders NOTHING beyond
the first row. Long prompts are unusable. pi wraps, navigates, and grows the
editor box; tart must match (BRIEF §8).

Grounding (verified by the architect 2026-10-12):
- tart: lib/tart/render/editor.rb (354 lines) is a SINGLE-LOGICAL-LINE editor
  — one @buffer string, no wrap, no visual rows; chat.rb's editor area
  renders it as one content row inside the bordered box.
- pi: packages/tui/src/components/editor.ts carries a full VISUAL-LINE MODEL:
  buildVisualLineMap(lastWidth) maps logical lines to wrapped visual rows
  (:445-453), findCurrentVisualLine, per-visual-row home/end (:661-685),
  sticky-column navigation with snappedFromCursorCol (:1480-1494). Word-wrap
  machinery (wrapSingleLine/breakLongWord) is already ported for the I33
  resource rows — the motif exists in-tree.
- Also in scope of pi's shape: real newlines (paste with newlines, and
  whatever pi uses to insert them interactively — verify in editor.ts),
  multi-line history entries, kill/yank ops operating across visual rows (the
  I26 lastAction discipline), and the editor box GROWING as content wraps
  (pi's bordered editor grows upward into the viewport; study how pi computes
  the dock budget as rows increase — chat-viewport.ts).

Shape: port the visual-line model into Tart::Render::Editor (logical lines ×
wrapped visual rows, cursor as logical position + visual navigation
equivalents of pi's), render multi-row editor content in the bordered box
with the box height following content (bounded by pi's layout rules), and
keep every existing op working across wrapped rows. Match pi's behavior at
each seam, not a re-invention: read editor.ts's cursor-motion family before
designing.

Gates: bundle exec rake + bundle exec ruby bench/seam_bench.rb green; s1–s9
exit 0 cold unchanged; new editor tests pinning: wrap rendering at a narrow
width (typed past EOL renders on row 2+), cursor up/down across wrapped rows
with sticky columns, home/end per visual row, kill-to-line-start/end on
wrapped rows, box growth/clamping, multi-line history recall. If the rig can
see it cheaply (post_settle_keys typing a long line, s9 precedent), add a
scenario; otherwise unit-pinned.

ENTRY P2

ITERATION: thinking-wiring

THE LIVE HANG (owner killed tart after multi-minute turns; pi finished the
same session in ~3.5 min): tart never sends any thinking/reasoning parameter,
so fireworks glm-5p3-flash runs its server-default thinking budget — runaway
generation. This un-parks the 2026-10-11 "request-side reasoning_effort
wiring PARKED (unverified live)" decision: it is now live-verified.

Evidence (all gathered 2026-10-12 by the architect):
- Session traces: tart turn 1 = 45,099 output tokens of which 45,076 thinking
  (8m48s wall) — ~/.tart/sessions/--Users-eric-architect-spaces-20261012-
  tmp-for-pi-testing-tart--/2026-10-12T18-45-45-427Z_*.jsonl. pi same prompt,
  same model: 11,764 reasoning (2m33s), later turns 7–727 reasoning —
  ~/.pi/agent/sessions/--...-pi--/2026-10-12T18-45-27-558Z_*.jsonl.
- Live A/B probe tmp/repro_thinking_budget.rb (still in the space's tmp/):
  identical small request, no thinking param → 453 completion tokens / 7.7s;
  with reasoning_effort:"high" → 24 tokens / 1.0s. The param demonstrably
  bounds thinking on fireworks.
- pi mechanism: packages/ai/src/api/openai-completions.ts:969-976 — generic
  branch sends `reasoning_effort = model.thinkingLevelMap[level] ?? level`
  when compat.supportsReasoningEffort (derives TRUE for fireworks —
  openai-completions.ts:1645-1648). The owner's ~/.pi/agent/models.json
  override maps every level to a string for glm-5p3-flash ("off"→"low" —
  this model cannot turn thinking off; the catalog's off is null).
- tart gaps: (1) no reasoning param is ever sent — Agent::Loop/bin/tart
  build the ruby_llm chat without any thinking option; the port HAS thinking
  levels (settings thinkingLevel, /thinking set+cycle, footer segment) but
  they never reach the wire. (2) lib/tart/agent/loop.rb:560-580
  strip_thinking_replay nils @raw_reasoning on every recorded assistant
  message because ruby_llm's replay shape (messages[n].reasoning) broke
  strict endpoints — but pi REPLAYS prior thinking in tool-call continuations
  (openai-completions.ts:611-627, thinking blocks keyed by signature ∈
  {reasoning, reasoning_content, reasoning_text}), which is why pi's turn 2+
  re-think near zero while tart's turn 2 burned another ~40K. Tart::Models
  (lib/tart/models.rb) must parse thinkingLevelMap from the catalog.

Shape: (1) wire the resolved thinking level to the request — for
OpenAI-compat providers send reasoning_effort via the model's
thinkingLevelMap (level "off" maps per catalog; null-off models send the
catalog's floor like pi's owner override does — follow pi's resolution code,
not assumptions). Extend the rig's MockLLM to assert the param arrives.
(2) Replace the strip with pi's replay protocol: send prior assistant
thinking back under the field the provider accepts — LIVE-VERIFY with a
small two-turn probe (tool-call continuation with and without
reasoning_content replay; measure thinking tokens like the A/B above)
before freezing the shape. Record the probe in the iteration Grounds.
(3) If ruby_llm cannot express the needed request fields, thread them at
the chat-creation seam it does support — search the gem (2.1.0) for its
request-parameter surface before concluding anything is impossible.

Gates: suite + bench green; s1–s9 exit 0 cold unchanged; mock-asserted
request pins (reasoning_effort present per level, off-floor behavior);
a live two-turn replay probe documented in Grounds; a unit pin that
recorded assistant messages keep their thinking for replay (no strip).
