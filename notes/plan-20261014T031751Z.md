ENTRY A (first — the owner's worst finding)

ITERATION: steering-queue

The port's mid-flight input handling diverges from pi in three coupled ways.
pi's architecture: submit-while-streaming calls session.prompt(text,
{streamingBehavior}) — extension commands execute IMMEDIATELY even during
streaming (agent-session.ts:1927-1934: `_tryExecuteExtensionCommand` runs
before any queueing), skill/prompt-template expansion happens before queueing
(:1947-1959), and what's left queues as either STEER or FOLLOW-UP. A steering
message is "delivered after the current assistant turn finishes executing its
tool calls, before the next LLM call" (agent-session.ts:2203-2208; the UI-side
mirror removes it from _steeringMessages on delivery, :1123-1126).

Owner findings this closes (problems.md items 4, 5, 7):

1. `/thinking` while streaming queued as a USER MESSAGE and was sent to the
   model. Root cause, verified: render/chat.rb submit —
   `return if !busy? && gate_thinking_level(text)` and
   `return if !busy? && @commands.dispatch(text)` — the !busy? gates make
   every slash command fall through to `@agent.push_message(text)` while
   streaming (chat.rb:961-963, :973-975). Fix to pi's shape: commands
   dispatch regardless of busy; expansion before queue.
2. Queued messages render above the editor with help text in pi — dim
   `Steering: <text>` / `Follow-up: <text>` rows + `↳ <key> to edit all
   queued messages` (interactive-mode.ts:4725-4739, pendingMessagesContainer),
   plus the streaming-state hints "to queue follow-up" / "to edit all queued
   messages" (:1044-1045). Keybinds app.message.followUp (handleFollowUp
   :4486+) and app.message.dequeue (handleDequeue →
   restoreQueuedMessagesToEditor :4743+, clearAllQueues :4708-4721; dequeue
   can optionally abort the run). The port has NONE of this display.
3. Queued message fired only after the assistant round ended completely. The
   port's push_message drains at the round boundary; pi delivers steering
   between tool-batch end and the next LLM call of the SAME run. Owner asked
   for trace verification: at spec time, capture a pi trace (or read
   agent-loop.ts drain sites) proving the delivery point, and pin the port's
   new drain point to it. Also port followUp mode (delivered only when the
   agent is fully done) and the compaction queue (messages submitted during
   compaction queue as steer, interactive-mode.ts:3371-3381, :4763+).

Shape (spec owns detail): the queue moves into the agent/session layer with
steer + followUp modes (pi's split); the loop drains steering after each
assistant turn's tool batch; submit dispatches commands busy-or-not; the
surface renders the queue rows + hints and binds dequeue/followUp keys;
session recording carries steering/followUp messages as user messages at
their actual delivery points.

Gates: battery + s1–s10 + probes + existing wire/session digests EXACT; a NEW
rig/mock scenario pinning steering delivery INSIDE a tool round (tool call →
steer → the steering text rides the next request of the SAME run, not a new
round) and the /thinking-while-streaming cure (command executes, nothing
queued to the model — assert the next request's user content does NOT contain
"/thinking"); unit pins on the queue display rows.

ENTRY B

ITERATION: paste-markers

Ported from pi's editor (packages/tui/src/components/editor.ts):

- Large paste = >10 lines OR >1000 chars → store the full text in a paste
  registry, insert ONLY a marker `[paste #1 +123 lines]` (line-count form) or
  `[paste #1 1234 chars]` (char form) at the cursor (:1296-1317).
- Submit expands markers via expandPasteMarkers over the joined text (:1090,
  :1366) — the wire gets the full content, the marker is display-only.
- Deleting a marker (backspace over it — PASTE_MARKER_SINGLE grapheme check,
  :1395-1419) drops the registry entry, renumbers higher ids in the registry
  AND renumbers every marker in the text.
- Small niceties in the same path: non-printable filtering, and pasting a
  path-like text (/ ~ .) after a word char prepends a space (:1291-1299).
- REGEXES: PASTE_MARKER_REGEX :32, PASTE_MARKER_SINGLE :35.

OWNER RULING EMBEDDED (beyond pi, sanctioned deviation — problems.md item 8):
pasting again immediately OVER a marker replaces it with the full text inline
(the claude-code behavior; pi does not have this). Test-pin it as the port's
own behavior.

Related backlog carried in: the I18-era "large-paste marker compaction cut"
(loop-closure item f) — the marker must survive session replay shape decisions
(the session records the EXPANDED text per pi; verify and pin).

Gates: battery; unit tests on the registry (insert marker, renumber on
delete, expansion at submit, paste-over-marker expand); wire digests EXACT on
existing scenarios; a new scripted scenario with a large pasted user turn
pinning the full content on the wire and the marker in the display buffer.

ENTRY C

ITERATION: resize-layout

Owner findings (problems.md items 1, 2): resize smaller and the header help
text ("ctrl+c interrupt/quit …") cuts off at the border instead of wrapping;
the ascii art cuts off; the editor input doesn't reflow until the cursor
moves. All three should react to sigwinch itself.

- Help/hints rows wrap at the CURRENT terminal width: pi's header is a live
  component re-laid-out on resize; the port freezes header rows into the
  scrollback at render. Shape (spec owns): the header block re-wraps on
  resize — the existing expandable-registration rebuild path (ctrl+o flip,
  I33) is the natural mechanism.
- Art width ladder (tart-identity UX, owner-directed): at header render pick
  from lib/tart/render/logos/ the widest art that FITS the terminal width;
  if the terminal is narrower than the smallest art, render the word "tart".
  Re-pick on every header render (boot, /new, resize rebuild). pi's analog
  shape: pi-logo.ts is a fixed tiny mark with piWordmark() fallback when the
  terminal can't render it (supportsPiLogo) — the ladder is the port's own
  collection logic.
- Editor input reflows on sigwinch: force the wrap recompute in the resize
  path (today it recomputes lazily on cursor movement).
- RECORDED DIVERGENCE, parked (do not fix here): pi re-wraps the WHOLE
  transcript on resize (components re-render); the port's scrollback is
  pre-wrapped frozen rows. Reopening that is its own program if the owner
  feels the pain — this entry fixes header + art + editor only.

Gates: battery; unit pins (hints wrap at narrow width; art ladder selection
per width incl. the wordmark floor; editor reflow on resize without cursor
movement); a rig resize scenario if cheap (tmux resize-pane mid-run; optional
— judge may waive if the rig can't express it, but the unit pins are
mandatory).
